# ADR-001: Ship the Events feature as a Drupal Recipe plus a companion module

- Status: Proposed (agent draft, to be reviewed and decided by me)
- Date: 2026-11-12

## Context

We need a reusable Events feature: content type, taxonomy, role, view,
aliases, styled output and sample content. It must:

- be added to a **fresh or existing** Drupal 11 site (minimal or standard)
  with **one command**
- survive being applied **twice**
- not break sites that already have a Tags vocabulary or an editor role
- keep its config clean (no UUIDs or `_core` keys)

Time box: about 10 hours. Stack: Drupal 11.4, Drush 13, DDEV.
Detailed findings are in [RESEARCH.md](RESEARCH.md).

## Options considered

### Option A: Recipe (`ls_events`) plus a small companion module

- Pros:
  - Applies to any existing site with `drush recipe`, and can be applied
    again.
  - Can reuse core recipes (`image_media_type`,
    `basic_html_format_editor`) instead of copying their config.
  - Config actions (`createIfNotExists`, `grantPermissions`,
    `placeBlockInDefaultTheme`) change other people's config without
    owning it.
  - Default content import is built in, and content is skipped by UUID on
    re-apply.
  - Composer `drupal-recipe` packaging with unpacking, so Pathauto
    becomes a root dependency.
  - Core test tooling (`RecipeTestTrait`).
  - This is the direction core is heading: Drupal CMS and the core
    profiles are moving to recipes.
- Cons:
  - Recipes can't contain code, so a separate module is needed for the
    SDC component and templates.
  - Once applied there is no link back to the recipe: no uninstall, no
    update path. Later changes need new recipes or update hooks.
  - Strict mode (the default) fails if a shipped config file differs on
    the site. Tested: a config action on config shipped by the same
    recipe breaks the second apply.
  - The API is still young; re-apply behaviour is listed as an open
    question in the initiative docs.

### Option B: Install profile

- Pros:
  - The traditional, well-documented way to ship a whole site setup.
  - Can contain code (hooks, `hook_install`) as well as config.
- Cons:
  - Only works at **install time**. It can't be applied to an existing
    site, which fails the core requirement.
  - A site has exactly one profile, so the feature couldn't be combined
    with other features or profiles.
  - No built-in default content (needs the contrib `default_content`
    module).
  - Core is moving profiles to recipes.

### Option C: Config-only module (`config/install` + `config/optional`)

- Pros:
  - Familiar. Installable on existing sites with `drush en`.
  - Can contain the SDC component and templates in the same module.
  - Uninstall removes the config it owns.
- Cons:
  - Installing fails with `PreExistingConfigException` if any of its
    config already exists.
  - Changing other config (e.g. granting permissions to roles) needs PHP
    in `hook_install`.
  - "Applying twice" isn't a concept: a second `drush en` does nothing.
  - No reuse of core recipes.
  - Default content needs the contrib `default_content` module.
  - The module then owns the content type's config, so uninstalling it
    can delete the content model along with its content.

## Decision

**Agent recommendation:** Option A, because it is the only option that
meets "apply to an existing site with one command, twice, without
conflicts" without custom PHP. The code it can't hold goes into a small
companion module (`ls_events_ui`), which the recipe installs via
`install:`.

## Consequences

- Easier:
  - One command adds the feature to any site.
  - Re-apply is safe as long as these rules hold:
    - config actions touch only config that other modules or recipes own
    - our own config uses our own machine names
    - content keeps fixed UUIDs
- Harder / trade-offs:
  - The companion module must be versioned and installed alongside the
    recipe (as a Composer package or a custom module in this repo).
  - There is no update path for sites that already applied an older
    version of the recipe.
  - The recipe test needs either `drupal/core-dev` (PHPUnit +
    `RecipeTestTrait`) or a scripted Drush check. This is decided in
    PLAN.md.
